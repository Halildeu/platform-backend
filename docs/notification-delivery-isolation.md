# Notification delivery isolation

Tracked by platform-mobile#9, backend PR1176 and platform-k8s-gitops#3793.

Domain event publication and notification HTTP delivery use independent persistent state. A successful fenced domain PUBLISHED transition and a unique notification job insertion commit in the same local transaction. A lost fence enqueues nothing. Failed handoff rolls back the transition; ordinary at-least-once Redis crash recovery remains unchanged.

A separate worker locks one job with PostgreSQL FOR UPDATE SKIP LOCKED during delivery. It has its own executor, retry counter (default 20), 30-second retry delay and terminal DEAD state. HTTP failure cannot republish a domain event or consume its retry budget. A process failure rolls back the job transaction; existing per-recipient intent idempotency keys protect retries after uncertain HTTP outcomes. This is not an exactly-once network delivery guarantee.

The queue stores only an event-outbox reference and delivery status. Deleting that event cascades to the job. Transcript erasure preserves domain events, so its worker locks the exact canonical occurrence with FOR SHARE and then re-reads the session-erasure marker. Meeting analysis deletion already cascades through the V7 event FK to the notification job; its worker checks the source and erasure marker without another source lock. A missing occurrence or visible erasure request terminates a surviving notification as DEAD / SOURCE_UNAVAILABLE without increasing attempts or altering the domain event. A newer occurrence cannot substitute for an erased one. No transcript or additional recipient snapshot is copied. Each attempt resolves authorized recipients again. Native summary delivery disabled by configuration pauses existing summary jobs without consuming attempts; assignment delivery continues. Disabled transcript notifications do not run their worker. Activation does not backfill already-published events from before this change.

Transcript lock order is notification job then canonical source row; transcript erasure/retention do not lock notification jobs. The source lock lasts through HTTP handoff commit, so deletion cannot complete during that handoff. Its erasure-marker check is a separate statement after acquiring the source lock, to see a prepare that committed while waiting even if prepare did not update the source row. Meeting delivery holds only the notification job lock; the deletion cascade cannot complete until that lock is released. Acquiring the meeting run lock after the job lock would invert the deletion lock order and is deliberately avoided. A meeting erasure request visible at admission suppresses handoff; a request that starts concurrently may follow an already admitted handoff. Neither path can recall a notification already accepted downstream or by FCM/APNs.

Migrations: meeting V16 and transcript V15 are additive. Preserve queue tables and data when rolling back application binaries. A rollback to the previous binary resumes its previous coupled delivery behavior and does not drain the new queue. Before rollout, inspect pending/DEAD domain events; this change does not automatically repair historic DEAD rows.

Verification: focused unit tests cover no HTTP on the domain publisher, lost-fence exclusion, isolated retry and transaction requirement. PostgreSQL regressions cover atomic handoff rollback, unique enqueue, concurrent lock exclusion, process-loss rollback, backoff, independent counters, real erasure/retention suppression, and holding the source row during handoff. Partial-recipient retries reuse stable intent identities and resolve the audience again; orchestrator intake tests exercise committed-first/rolled-back-second recipient replay. Live TEST rollout and physical FCM/APNs delivery are separate acceptance gates.
